## 1. 긴급 확인 필요 (Phase 1 범위 결정)

### 1.1 파일 버전 관리 구현 범위

**현재 상황:**
- 사용자가 파일 버전 관리의 의미와 우선순위에 대해 질문함
- "정확히 어떤 의미인가?"

**문제점:**
- 논문지도활동에서 학생이 새 파일을 업로드할 때마다 이전 버전의 교수 피드백과 연결이 끊김
- 교수가 이전에 어떤 피드백을 주었는지 확인 어려움
- 학생이 교수 피드백을 어떻게 반영했는지 추적 불가능

**제안된 해결 방안:**

| 방안 | 구현 내용 | 예상 공수 | Phase |
|------|----------|---------|-------|
| 방안 1 (상세) | 버전별 피드백 매핑, 학생 반영 내용 표시 | 5일 | Phase 3 |
| 방안 2 (단순) | 버전 번호 + 이전 제출물 참조만 | 2일 | Phase 1 |

**확인 필요:**
1. Phase 1에 포함할 것인가, Phase 3로 미룰 것인가?
2. 포함한다면 방안 1(상세), 방안 2(단순) 중 어느 것을 선택할 것인가?
3. 재심 프로세스와 비교했을 때 우선순위는?

**권장 사항:**
- **Phase 1**: 방안 2 (단순 버전 추적) 구현 (2일)
- **Phase 3**: 방안 1 (상세 피드백 매핑) 구현 (5일)
- **근거**: 재심은 법정 절차로 필수이나, 버전 관리는 편의성 개선 기능

## 2. 비즈니스 규칙 확인 필요

### 2.1 재심 횟수 제한

**질문:**
- 한 단계에서 재심은 최대 몇 회까지 허용되는가?

**현재 메일 내용:**
- 석사: 본심 1회, 조건부합격자만 재심
- 박사: 본심 2회, 조건부합격자 재심

**확인 필요:**
- 재심에서 또 조건부합격이 나오면 재재심이 가능한가?
- 최대 재심 횟수 제한이 있는가? (예: 재심 1회까지, 재재심 불가)

**영향:**
- ExaminationHistory.examRound 최댓값 설정
- UI에서 재심 횟수 표시 및 제한 로직

**우선순위:** P1 (Phase 1 시작 전 확인 필요)

### 2.2 재신청 횟수 제한

**질문:**
- 같은 단계에서 불합격 후 재신청은 최대 몇 회까지 허용되는가?

**현재 메일 내용:**
- 불합격 시 다음 학기 재신청 가능

**확인 필요:**
- 무제한 재신청 가능한가?
- 재신청 횟수 제한이 있는가? (예: 동일 단계 재신청 3회까지)
- 재신청 시 이전 심사위원 구성을 재사용할 수 있는가?

**영향:**
- ThesisApplication.previousApplications 배열 크기 제한
- UI에서 재신청 가능 여부 표시

**우선순위:** P1 (Phase 2 시작 전 확인 필요)

### 2.3 심사위원 변경 가능 여부

**질문:**
- 재심 시 심사위원을 변경할 수 있는가?

**현재 메일 내용:**
- 예비심사 N차, 본심사 N차는 처음 구성한 위원이 동일하게 진행

**확인 필요:**
- **Case 1**: 재심(대면) - 전체 심사위원 평가 시
  - 초기 심사위원회와 동일한 구성원이어야 하는가?
  - 일부 위원 변경 가능한가?

- **Case 2**: 재심(서면) - 심사위원장만 평가 시
  - 심사위원장 변경 가능한가?

**영향:**
- CommitteeAssignment 테이블 구조
- 재심 정보 설정 UI (심사위원 변경 옵션)

**우선순위:** P2 (Phase 1 구현 중 확인 가능)

### 2.4 지도교수 위임 기능 상세

**질문:**
- 서면 재심 시 "지도교수에게 위임" 기능의 정확한 동작 방식은?

**현재 메일 내용:**
> "재심(서면): 심사위원(장)이 승인, 지도교수에게 위임하여 승인할 수 있음"

**확인 필요:**
1. **위임 시점:**
   - 조건부합격 판정 시 심사위원장이 미리 위임 여부를 결정하는가?
   - 재심 평가 시점에 심사위원장이 위임을 결정하는가?

2. **위임 방식:**
   - 심사위원장이 "위임" 버튼을 클릭하면 지도교수에게 권한이 넘어가는가?
   - 위임 후 심사위원장은 평가할 수 없는가?

3. **평가 책임:**
   - 위임 시 최종 평가 책임은 지도교수에게 있는가?
   - 심사위원장이 위임 후에도 결과를 확인/승인해야 하는가?

**구현 방향 제안:**
```javascript
// Option A: 조건부합격 판정 시 미리 위임 결정
reexamInfo: {
  method: '서면',
  evaluationType: 'advisor_delegated',  // 위임
  delegatedTo: 'ADVISOR_ID'
}

// Option B: 재심 평가 시점에 위임
reexamInfo: {
  method: '서면',
  evaluationType: 'chair_only',  // 초기값
  canDelegate: true              // 위임 가능 플래그
}
// 심사위원장이 "지도교수에게 위임" 버튼 클릭 시
// → evaluationType을 'advisor_delegated'로 변경
```

**우선순위:** P2 (Phase 2에서 구현)

## 3. 기술적 확인 필요

### 3.1 알림 발송 채널

**질문:**
- 재심/재신청 관련 알림을 어떤 방식으로 발송할 것인가?

**확인 필요:**
- **이메일**: 발송 가능한가? 이메일 템플릿은?
- **SMS**: 발송 가능한가? SMS 비용은?
- **시스템 알림**: 시스템 내 알림만 표시하는가?
- **복수 채널**: 여러 채널을 동시에 사용하는가?

**알림 종류:**
1. 조건부합격 → 학생에게 재심 안내
2. 재심 제출 완료 → 교수에게 재심 평가 요청
3. 재심 평가 완료 → 학생에게 합격/불합격 통지
4. 불합격 → 학생에게 재신청 안내
5. 재신청 접수 → 관리자에게 심사위원 구성 요청
6. 심사위원 구성 완료 → 학생에게 논문 제출 안내

**우선순위:** P2 (Phase 2 구현 전 확인)

### 3.3 D-Collection 제출 관리

**질문:**
- 본심사 합격 후 D-Collection 제출을 시스템에서 관리할 것인가?

**현재 회의록:**
> "디컬렉션을 제출 안 하면 그다음에 다시 제출해야 돼요."
> "그거를 제출하는 거를 이 논문 지도 시스템에서 관리를 해야 되는지 여부를 여쭤본 거예요."

**확인 필요:**
1. **관리 범위:**
   - 시스템에서 D-Collection 제출 단계를 추가할 것인가?
   - 외부 링크로 연결하여 안내만 할 것인가?

2. **제출 확인:**
   - D-Collection 제출 완료 여부를 시스템에서 확인해야 하는가?
   - 제출하지 않으면 졸업 처리가 안 되는가?

**구현 방향 제안:**

| 방안 | 구현 내용 | 공수 |
|------|----------|------|
| 방안 A | D-Collection 제출 단계를 워크플로우에 추가 | 3일 |
| 방안 B | 본심사 합격 후 안내 메시지만 표시 (외부 링크) | 0.5일 |

**우선순위:** P3 (Phase 3에서 결정 가능)

### 5.2 중간 단계 불합격 처리 정책

**질문:**
- 중간 단계에서 불합격 판정 후 다음 단계로 진행하는 것을 시스템에서 어떻게 처리할 것인가?

**현재 상황:**
- **회의록**: "불합격해도 뒤로는 넘겨야 되잖아요" (교수 판단으로 진행 가능)
- **메일**: "불합격은 해당 단계에서 종결, 다음단계 미진행" (원칙)

**확인 필요:**
1. **시스템 구현:**
   - 불합격 판정 시 "다음 단계 이동" 버튼을 제공할 것인가?
   - 불합격 + 다음 단계 이동 시 기록을 어떻게 남길 것인가?

2. **운영 가이드:**
   - 교수에게 어떤 기준으로 안내할 것인가?
   - 불합격 시 조건부합격을 사용하도록 유도할 것인가?

**구현 방향 제안:**
```
Option A (원칙 준수):
- 불합격 → 단계 종결 (다음 단계 이동 불가)
- 조건부합격 → 재심 → 합격 시 다음 단계 이동
- 교수 판단 여지 없음

Option B (유연한 운영):
- 불합격 판정 후 "다음 단계 이동" 체크박스 제공
- 체크 시: 불합격 기록 + 코멘트 + 다음 단계 이동
- 미체크 시: 불합격 기록 + 단계 종결
```

**우선순위:** P0 (Phase 1 시작 전 명확한 결정 필요)
