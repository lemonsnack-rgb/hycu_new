## 2. 신규 기능 구현 난이도 분석

### 2.1 ExaminationHistory 테이블 (P0 - 핵심)

#### 현재 상태
```javascript
// 현재 없음
// GuidanceSubmission에 일부 유사 개념 존재 (version, feedbackDate)
```

#### 필요한 변경
```javascript
ExaminationHistory {
  id: string
  studentId: string
  stageOrder: number              // ← currentStageOrder와 연동
  stageName: string
  examRound: number               // ← 신규 개념 (핵심)
  examType: 'initial' | 'reexam'  // ← 신규 개념

  // 심사 정보
  committeeChair: string
  committeeMembers: string[]      // ← 배열 구조
  submissionDate: string
  evaluationDate: string
  semester: string

  // 평가 결과
  result: '합격' | '조건부합격' | '불합격'  // ← 신규 개념

  // 재심 정보 (조건부합격 시만)
  reexamInfo: {
    method: '대면' | '서면'       // ← 신규 개념
    evaluationType: 'full' | 'chair_only'  // ← 신규 개념
    deadline: string
    requirements: string
    status: 'pending' | 'submitted' | 'completed'
  } | null

  applicationId: string           // ← ThesisApplication 연동
}
```

#### 구현 난이도: 🔴 **중상** (4/5)

**난이도 높은 이유**:
1. **기존 데이터 구조와 연동 복잡**:
   - ExamSchedule과 역할 중복 가능성
   - EvaluationTemplate과 연동 필요
   - StudentThesisStage.currentStageOrder와 동기화 필요

2. **신규 개념 다수**:
   - examRound (심사 차수)
   - result (합격/조건부합격/불합격)
   - reexamInfo (재심 정보 전체)

3. **데이터 마이그레이션 필요**:
   - 기존 ExamSchedule 데이터를 ExaminationHistory로 변환 필요
   - 기존 평가 데이터가 어디에 있는지 확인 필요

#### 리스크
- 🔴 **High**: 기존 ExamSchedule과 충돌 가능
- 🟡 **Medium**: 평가 데이터 이관 실패 시 이력 손실
- 🟡 **Medium**: examRound 계산 로직 오류 시 데이터 무결성 깨짐

#### 대응 방안
1. ExamSchedule은 "일정 관리"로 역할 유지, ExaminationHistory는 "평가 이력"으로 분리
2. 초기 버전은 신규 데이터만 ExaminationHistory에 저장 (기존 데이터 이관 선택 사항)
3. getNextExamRound() 함수 단위 테스트 필수

#### 현재 상태
```javascript
// 현재 없음

ResearchProposal {

  method: string

  status: 'pending' | 'assigned'
```

#### 필요한 변경
```javascript
ThesisApplication {
  id: string
  studentId: string
  stageOrder: number              // 어느 단계의 신청인지
  semester: string                // 신청 학기
  applicationDate: string

  // 재신청 구분
  isReapplication: boolean        // ← 신규 개념
  previousApplications: string[]  // ← 신규 개념 (이력 추적)

  // 논문 정보 (학생 입력)
  title: string
  abstract: string                // ← ResearchProposal에 없음
  keywords: string[]              // ← ResearchProposal에 없음

  // 논문 제출 (학생 업로드)

  submittedAt: string | null

  // 심사 일정 (심사위원장 설정)
  examDate: string | null
  examLocation: string | null      // '온라인' | '오프라인'
  examScheduledAt: string | null

  // 신청 상태
  status: 'application_submitted' | 'committee_assigned' |
          'thesis_submitted' | 'exam_scheduled' |
          'under_evaluation' | 'completed' | 'failed'  // ← 신규 개념 (상태 기반 워크플로우)

  closedAt: string | null
}
```

#### 구현 난이도: 🔴 **중상** (4/5)

**난이도 높은 이유**:
1. **전체 라이프사이클 관리**:
   - 7단계 상태 전환 로직 (FSM - Finite State Machine)
   - 각 상태별 화면 및 API 필요

2. **기존 모델과 통합**:
   - ResearchProposal + AdvisorAssignment + ExamSchedule + GuidanceSubmission을 하나로 통합
   - 기존 기능과의 충돌 가능성

3. **재신청 복잡도**:
   - previousApplications 배열 관리
   - 이전 신청 이력 조회 및 표시

#### 리스크
- 🔴 **High**: 기존 ResearchProposal 프로세스와 충돌
- 🟡 **Medium**: 상태 전환 로직 버그 (잘못된 상태로 진입)
- 🟡 **Medium**: previousApplications 배열 관리 오류

#### 대응 방안
1. **Phase별 구현**:
   - Phase 1: ExaminationHistory만 구현 (재심)
   - Phase 2: ThesisApplication 구현 (재신청)
2. **기존 프로세스 유지**: ResearchProposal은 초기 신청 용도로 유지, ThesisApplication은 본심사 이후만 적용
3. **상태 전환 로직 명확화**: FSM 다이어그램 작성 + 단위 테스트

### 2.3 워크플로우 무결성 보장 (P0 - 핵심 설계)

#### 현재 상태
```javascript
ThesisStage {
  id: 'TS001',
  stages: [
    { order: 1, name: '연구계획서', ... },
    { order: 2, name: '예비심사 1차', ... },
    { order: 3, name: '본심사', ... },
    { order: 4, name: '최종논문', ... }
  ]
}

StudentThesisStage {
  studentId: 'STU001',
  thesisStageId: 'TS001',
  currentStageOrder: 2,           // 현재 예비심사 1차
  // customStages 없음 - 모든 학생이 템플릿 그대로 사용
}
```

#### 문제점
📌 **재심사 구현방식_결정.md에서 제안한 방식**:
```javascript
StudentThesisStage {
  customStages: [                 // ← 학생별 독립 단계 목록
    { order: 1, name: '연구계획서' },
    { order: 2, name: '본심사' },
    { order: 2.5, name: '본심사(재심)', isReexamStage: true },  // ← 동적 추가
    { order: 3, name: '최종논문' }
  ],
  currentStageOrder: 2.5          // ← 재심 진행 중
}
```

⚠️ **이 방식의 문제점**:
1. 워크플로우 템플릿 무결성 깨짐
2. 학생마다 다른 워크플로우 → 감사 추적 불가
3. order 재조정 복잡 (2.5, 3.5, ...)
4. 버그 발생 가능성 높음

#### 최종 해결 방안 (재심사_구현방식_최종.md)
```javascript
// ThesisStage: 변경 없음 (모든 학생 공통)
ThesisStage {
  stages: [
    { order: 1, name: '연구계획서', allowReexam: false },
    { order: 2, name: '본심사', allowReexam: true },      // ← 재심 허용 플래그만 추가
    { order: 3, name: '최종논문', allowReexam: false }
  ]
}

// StudentThesisStage: 변경 없음 (currentStageOrder만 사용)
StudentThesisStage {
  studentId: 'STU001',
  thesisStageId: 'TS001',
  currentStageOrder: 2,           // ← 재심 중에도 2 유지!
}

// ExaminationHistory: 재심 차수로 관리
ExaminationHistory [
  { examRound: 1, result: '조건부합격', stageOrder: 2 },
  { examRound: 2, examType: 'reexam', result: '합격', stageOrder: 2 }
]
```

#### 구현 난이도: 🟢 **하** (2/5)

**난이도 낮은 이유**:
1. **기존 구조 그대로 유지**: ThesisStage, StudentThesisStage 변경 최소
2. **단순 필드 추가**: allowReexam 플래그만 추가
3. **별도 테이블 관리**: ExaminationHistory에서 재심 차수 관리

#### 리스크
- 🟢 **Low**: 기존 코드 영향 최소
- 🟢 **Low**: 워크플로우 무결성 보장

#### 대응 방안
1. ThesisStage.stages[].allowReexam 필드 추가 (boolean, default: false)
2. 관리자 화면에서 단계별 재심 허용 여부 설정 UI 제공
3. currentStageOrder는 절대 동적으로 변경하지 않음 (재심 중에도 유지)

### 2.4 재심 차수 관리 (getNextExamRound 함수)

#### 현재 상태
```javascript
// 현재 없음
// GuidanceSubmission에 version 개념만 존재
GuidanceSubmission {
  version: number  // 1, 2, 3, ...
}
```

#### 필요한 변경
```javascript
function getNextExamRound(studentId, stageOrder, applicationId) {
  // 1. ExaminationHistory 조회
  const histories = ExaminationHistory.filter(h =>
    h.studentId === studentId &&
    h.stageOrder === stageOrder &&
    h.applicationId === applicationId  // ← 재신청 시 1로 리셋하기 위해 필요
  );

  // 2. 최대 examRound 찾기
  if (histories.length === 0) {
    return 1;  // 첫 심사
  }

  const maxRound = Math.max(...histories.map(h => h.examRound));
  return maxRound + 1;
}
```

#### 구현 난이도: 🟢 **하** (2/5)

**난이도 낮은 이유**:
1. 단순 조회 및 계산 로직
2. 기존 GuidanceSubmission.version과 유사한 개념

#### 리스크
- 🟡 **Medium**: applicationId 없이 조회하면 재신청 시 examRound가 계속 증가 (1→2→3이 아닌 1→2→3→4→5...)

#### 대응 방안
1. **반드시 applicationId와 함께 조회**: 재신청은 새 ThesisApplication이므로 examRound=1부터 시작
2. 단위 테스트 필수:
   - 이력 없음 → 1
   - 이력 1건(examRound=1) → 2
   - 이력 3건(examRound=1,2,3) → 4
   - 재신청(새 applicationId) → 1

### 2.6 재심 평가 권한 관리 (canEvaluateReexam)

#### 현재 상태
```javascript
// 현재 권한 관리는 Role/Permission 기반
// 심사위원 여부만 체크 (chair vs member 구분 없음)
```

#### 필요한 변경
```javascript
function canEvaluateReexam(professorId, examHistory) {
  // 초기 심사는 모든 위원 평가 가능
  if (examHistory.examType !== 'reexam') {
    return examHistory.committeeMembers.includes(professorId);
  }

  // 재심 시 evaluationType 확인
  const reexamInfo = examHistory.reexamInfo;

  if (reexamInfo.evaluationType === 'full') {
    // 전체 심사위원 평가 가능
    return examHistory.committeeMembers.includes(professorId);
  }

  if (reexamInfo.evaluationType === 'chair_only') {
    // 심사위원장만 평가 가능
    return examHistory.committeeChair === professorId;
  }

  return false;
}
```

#### 구현 난이도: 🟢 **하** (2/5)

**난이도 낮은 이유**:
1. 단순 조건 분기 로직
2. 기존 권한 체크 로직과 유사

#### 리스크
- 🟡 **Medium**: 권한 체크 누락 시 평가 버튼이 모든 교수에게 표시

#### 대응 방안
1. 교수 화면 진입 시 반드시 canEvaluateReexam() 호출
2. 버튼 표시/숨김 로직 명확화
3. API 레벨에서도 권한 체크 이중화
