# 재심사 구현 방식 결정

## 결론: 재심사는 **별도의 지도단계**로 생성

---

## 1. 현재 시스템 구조 분석

### 1.1 핵심 데이터 구조
```javascript
StudentThesisStage {
  studentId: 'STU001',
  thesisStageId: 'TS001',        // 워크플로우 템플릿 ID
  currentStageOrder: 2,           // 현재 단계 번호 (순차적)
  currentStageName: '중간논문',
  currentStageType: 'review',
  canProceed: boolean
}

ThesisStage {
  id: 'TS001',
  name: '석사 표준 과정',
  stages: [
    { order: 1, name: '연구계획서' },
    { order: 2, name: '중간논문' },
    { order: 3, name: '예비심사' },
    { order: 4, name: '본심사' },
    { order: 5, name: '최종논문' }
  ]

```

### 1.2 단계 이동 로직
- 관리자가 `currentStageOrder`를 변경 (수동)
- 순차적 진행: 1 → 2 → 3 → 4 → 5
- **상태 필드 없음** (진행중/재심사중/완료 등)

## 2. 두 가지 구현 방식 비교

### 방식 A: 재심사를 별도의 지도단계로 생성 ⭐ (선택)

#### 구조
```
워크플로우 (석사):
1. 연구계획서 (order: 1)
2. 예비심사 1차 (order: 2)
3. 예비심사 2차 (order: 3)
4. 본심사 (order: 4)
5. 본심사(재심) (order: 5) ← 조건부합격 시 자동 생성
6. 최종논문 (order: 6)
```

#### 동작 흐름
```
학생이 본심사 제출 (order: 4)
    ↓
교수들이 평가
    ↓
[합격] → order: 6 (최종논문)로 이동
[조건부합격] → order: 5 (본심사 재심) 단계 자동 생성 후 이동
    ↓
학생이 수정논문 제출 (order: 5)
    ↓
재심 평가
    ↓
[합격] → order: 6 (최종논문)로 이동
[불합격] → order: 4 유지, 다음 학기 재신청
```

#### 장점
- ✅ **기존 코드 재사용**: 단계 이동 로직 그대로 사용
- ✅ **구현 간단**: 워크플로우 템플릿에 재심 단계만 추가
- ✅ **자동 이력 관리**: 재심이 별도 단계이므로 이력 추적 자동
- ✅ **심사위원 배정 재사용**: 기존 배정 로직 그대로 사용
- ✅ **학생 화면 명확**: "본심사(재심)" 단계로 표시

#### 단점
- ⚠️ 워크플로우가 길어짐 (단계 수 증가)
- ⚠️ "재심은 별도 단계가 아니다"라는 개념적 이해와 다름

#### 구현 복잡도: ★☆☆☆☆ (매우 낮음)
```javascript
// 기존 단계 이동 함수 그대로 사용 가능

  const student = getStudent(studentId);
  student.currentStageOrder = newOrder;
  // 끝!
}

if (result === '조건부합격') {
  const reExamOrder = currentOrder + 1; // 다음 단계가 재심
  changeStage(studentId, reExamOrder);
}
```

### 4.3 조건부합격 처리 로직 (동적 생성)

```javascript
// 평가 완료 후 결과 처리
function processEvaluationResult(studentId, stageOrder, result) {
  const student = mockStudentStageAssignments.find(s => s.studentId === studentId);
  const workflow = mockThesisStages.find(w => w.id === student.thesisStageId);
  const currentStage = workflow.stages.find(s => s.order === stageOrder);

  if (result === '합격') {
    // 다음 정규 단계로 이동 (학생의 customStages 기준)
    const nextOrder = getNextRegularStageOrder(student, stageOrder);
    changeStage(studentId, nextOrder);

  } else if (result === '조건부합격') {
    // 해당 단계가 재심 가능한지 확인
    if (!currentStage.allowReexam) {
      // 재심 불가 단계는 불합격 처리
      student.canProceed = false;
      return;
    }

    // 1. 학생의 customStages에 재심 단계 동적 추가
    const reexamStage = {
      order: stageOrder + 0.5,  // 중간 순서 (예: 4 → 4.5 → 5)
      name: `${currentStage.name}(재심)`,
      type: 'reexam',
      isReexamStage: true,
      originalStageOrder: stageOrder,
      createdAt: new Date().toISOString(),
      reexamInfo: {
        method: '대면' | '서면',
        date: '2026-02-15',
        requirements: '연구방법론 보완 필요'
      }
    };

    // 2. 기존 단계들의 order 재조정 (재심 이후 단계들 +1)
    student.customStages.forEach(stage => {
      if (stage.order > stageOrder && !stage.isReexamStage) {
        stage.order += 1;
      }
    });

    // 3. 재심 단계 삽입
    student.customStages.push(reexamStage);
    student.customStages.sort((a, b) => a.order - b.order);

    // 4. 학생을 재심 단계로 이동
    changeStage(studentId, reexamStage.order);

  } else if (result === '불합격') {
    // 현재 단계 유지
    student.canProceed = false;
  }
}

// 다음 정규 단계 찾기 (재심 단계 제외)
function getNextRegularStageOrder(student, currentOrder) {
  const nextStage = student.customStages.find(s =>
    s.order > currentOrder && s.isReexamStage !== true
  );
  return nextStage ? nextStage.order : null;
}
```

## 6. 예상 질문과 답변

**Q: 재심을 별도 단계로 만들면 워크플로우가 복잡해지지 않나요?**
A: 네, 단계 수가 늘어납니다. 하지만 구현이 훨씬 간단하고 안정적입니다. 복잡도는 UI 표시로 해결 가능합니다. (예: "본심사" 단계 안에 "재심" 서브 단계 표시)

**Q: 학생이 재심 단계를 보면 혼란스러워하지 않을까요?**
A: "본심사(재심)" 또는 "본심사 - 재심"으로 명확히 표시하면 됩니다. 오히려 "재심 중" 상태보다 명확할 수 있습니다.

**Q: N차 재심은 어떻게 처리하나요?**
A: 재심 2차가 필요하면 "본심사(재심2)" 단계를 추가로 생성하면 됩니다. (드물게 발생하므로 필요 시 수동 추가)

**Q: 나중에 "상태 관리" 방식으로 전환할 수 있나요?**
A: 가능합니다. 하지만 현재 시스템 구조에서는 별도 단계 방식이 최적입니다.

**트레이드오프**:

- 개념적으로 "별도 단계"가 아님 → 실용성 우선

**다음 단계**:
학교에 이 방식을 설명하고 승인받은 후 개발 진행
