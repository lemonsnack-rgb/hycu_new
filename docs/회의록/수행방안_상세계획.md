## 1. 개요

### 1.1 작성 배경

2026년 1월 23일(목, 금) 양일간 진행된 회의와 이후 받은 한양사이버대학교 대학원교학팀 메일을 통해 다음과 같은 핵심 요구사항을 확인했습니다:

**학교에서 요청하신 주요 사항**:
1. 심사는 교수님(또는 심사위원회)이 직접 평가하고, 행정직원이 대신 입력하는 방식은 지양
2. 예비심사나 본심사를 여러 차례(1차, 2차, 3차) 할 때 심사위원을 매번 새로 구성하지 않고 처음 구성한 위원으로 계속 진행
3. "조건부합격" 제도 도입 - 불합격은 아니지만 수정 후 재심사 필요
4. 평가표에 서술형, 척도형 평가 방식 추가
5. 논문 제출 시 수정전후대비표 같은 부속서류도 함께 제출

### 1.2 목적

이 문서의 목적은 다음과 같습니다:
- 학교 요구사항을 정확히 반영하면서도
- 현재 개발된 시스템을 크게 뜯어고치지 않고
- 심사 프로세스를 자동화하여 관리자의 손이 덜 가도록 하는 것

### 1.3 기본 방향

**핵심 3가지 원칙**:

1. **최소 변경**: 현재 시스템의 기본 틀(워크플로우 구조)은 그대로 유지
2. **자동화 우선**: 심사가 끝나면 자동으로 다음 단계로 넘어가도록 구현
3. **유연한 대안**: 학교 요청을 그대로 구현하기 어려운 경우, 목적을 달성할 수 있는 합리적인 대안 제시

## 2. 요구사항 분석

### 2.1 한양대 메일 핵심 요청사항

#### 2.1.1 심사주체 명확화 (최우선)

**학교 요청**:
> "해당 단계의 심사자(지도교수, 심사위원회)가 직접 평가 수행하고, 평가 없이 단계 승급하거나 행정직원이 평가 결과를 입력하는 구조는 지양"

**의미**:
- 모든 논문 단계(연구계획서, 예비심사, 본심사 등)마다 평가표가 있어야 함
- 교수님이 평가표를 작성해야만 다음 단계로 넘어갈 수 있음
- 관리자는 현황을 보기만 하고, 직접 "통과" 버튼을 누르지 않음

**현재 문제**:
- 일부 단계에서 평가표 없이 관리자가 수동으로 단계를 이동시키고 있음

#### 2.1.2 심사위원 구성 관리

**학교 요청**:
> "예비심사 N차는 본심사 N차의 경우, 처음 구성한 위원이 동일하게 진행. 기존 구성 내역을 불러와 적용할 수 있는 기능 제공"

**의미**:
- 예를 들어 예비심사를 3번(1차, 2차, 3차) 한다면
- 1차 때 심사위원 3명을 정하면
- 2차, 3차도 같은 3명이 심사하는 것이 원칙
- 단, 시스템에서는 매번 새로 구성할 수도 있지만, "이전 차수 심사위원 불러오기" 기능 제공

**예외 사항**:
- 프로포절 심사위원과 예비심사 심사위원은 다를 수 있음
- 즉, 큰 단계가 바뀔 때는 심사위원을 새로 구성 가능

#### 2.1.3 조건부합격 처리 (신규)

**학교 요청**:
석사 본심사를 예로 들면:

```
① 합격 → 논문 과정 완료
② 조건부합격 → 수정 후 재심사
   - 대면 재심: 심사위원 전원이 모여서 수정된 논문 다시 심사
   - 서면 재심: 심사위원장 또는 지도교수가 서면으로 확인 후 승인
③ 불합격 → 다음 학기에 다시 신청
```

박사 본심사는 2차까지 있음:

```
본심 1차:
  ① 합격 → 본심 2차로 진행
  ② 조건부합격 → 본심 2차에서 같이 재심사
  ③ 불합격 → 다음 학기 재신청

본심 2차:
  ① 합격 → 논문 과정 완료
  ② 조건부합격 → 서면 재심
  ③ 불합격 → 다음 학기 재신청
```

**의미**:
- 기존 합격/불합격 2가지 외에 "조건부합격" 추가
- 조건부합격이면 학생이 논문을 수정해서 다시 제출
- 재심사 방법은 대면(다시 모여서 심사) 또는 서면(문서로만 확인)
- 재심 제출 기한은 심사위원장이 정함

#### 2.1.4 평가표 유형 추가

**학교 요청**:
> "서술형 평가 추가: 심사자 서술형 의견 입력, 종합평정"
> "척도형 평가 추가: 현재 사용 중인 양식 참조"

**의미**:

**1) 서술형 평가표**:
- 점수가 아닌 글로 평가
- 예: "연구 주제가 명확하고 실현 가능한가?" → 교수님이 자유롭게 의견 작성
- 마지막에 합격/불합격 판정

**2) 척도형 평가표**:
- 5단계 평가 (매우 미흡 / 미흡 / 보통 / 우수 / 매우 우수)
- 여러 항목 평가 후 전체적으로 판단

**3) 점수형 평가표** (기존):
- 항목별로 점수 부여 (예: 연구주제 20점, 연구방법 30점)
- 총점이 기준점 이상이면 합격

#### 2.1.5 부속서류 제출

**학교 요청**:
> "N차, 재심의 경우 수정전후대비표 등 부속서류 제출"
> "학생은 논문 + 부속서류 제출, 교수/관리자는 논문다운로드 버튼으로 일괄 다운로드"

**의미**:
- 학생이 논문을 제출할 때
  - 주 논문 1개 (필수)
  - 부속서류 여러 개 (선택) - 수정전후대비표, 연구윤리서약서 등
- 교수님이나 관리자는 개별 파일을 각각 다운로드하여 확인

### 2.2 회의록 주요 논의사항

#### 2.2.1 단계 자동 이동
- 모든 심사위원이 평가를 완료하면 자동으로 다음 단계로 이동
- 관리자가 수동으로 "다음 단계" 버튼을 누를 필요 없음

#### 2.2.2 지도교수 단독 심사
- 어떤 단계는 심사위원회가 아니라 지도교수 혼자 평가
- 예: 논문작성계획서는 지도교수만 확인
- 이 경우 지도교수가 평가하면 바로 다음 단계로 이동

#### 2.2.3 학생이 제출한 파일 삭제 조건
- 학생이 논문을 제출했는데 잘못 올렸다면?
- 교수님이 아직 안 보셨으면: 삭제 가능
- 교수님이 이미 보셨으면: 삭제 불가능 (교수님이 확인 중이므로)

#### 2.2.4 학생도 피드백에 답변 가능
- 교수님이 "이 부분 수정하세요"라고 피드백을 남김
- 학생이 새 버전 제출할 때 "여기 이렇게 수정했습니다" 표시 가능
- 교수님이 새 버전 볼 때 학생의 수정 사항을 쉽게 확인

### 2.3 요구사항 우선순위 정리

| 분류 | 요구사항 | 출처 | 중요도 |
|------|----------|------|--------|
| 심사자 직접 평가 | 모든 단계에 평가표, 자동 이동 | 메일 | 최우선 |
| 조건부합격 | 재심 프로세스 (대면/서면) | 메일 | 최우선 |
| 심사위원 불러오기 | N차 심사위원 복사 기능 | 메일 | 중요 |
| 평가표 확장 | 서술형/척도형 추가 | 메일 | 중요 |
| 부속서류 | 여러 파일 업로드/다운로드 | 메일 | 중요 |
| 지도교수 단독 | 심사위원 없이 지도교수만 평가 | 회의 | 중요 |
| 제출물 삭제 조건 | 교수 확인 전에만 삭제 가능 | 회의 | 개선 |
| 학생 답변 기능 | 교수 피드백에 학생 답변 | 회의 | 개선 |

## 3. 현재 시스템 이해

### 3.1 시스템 구조 (레고 블록 비유)

현재 시스템은 "레고 블록"처럼 만들어져 있습니다:

**1단계: 레고 블록 만들기 (단계 유형)**
- "연구계획서 제출" 블록
- "예비심사" 블록
- "본심사" 블록
- 등등...

**2단계: 레고 블록 조립하기 (워크플로우)**
- 석사 과정: 연구계획서 → 예비심사 1차 → 예비심사 2차 → 본심사 → 최종논문
- 박사 과정: 연구계획서 → 프로포절 → 예비심사 1~3차 → 본심사 1차 → 본심사 2차 → 최종논문

**3단계: 학생에게 적용**
- 각 학생에게 석사 과정 또는 박사 과정 배정
- 학생은 순서대로 단계를 진행

### 3.2 현재 구현된 기능

**✅ 이미 개발된 것**:
- 레고 블록(단계 유형) 만들기
- 레고 블록 조립해서 워크플로우 만들기
- 워크플로우를 학생에게 배정
- 평가표 시스템 기본 구조
- 심사위원 배정 기능
- 학생 논문 제출 기능
- 교수 피드백 기능 (PDF에 코멘트 달기)

**⚠️ 수정이 필요한 것**:
- 평가표 "없음" 옵션 → 모든 단계에 평가표 필수로 변경
- 수동 단계 이동 → 자동 이동으로 변경
- 합격/불합격 2가지 → 조건부합격 추가
- 파일 1개만 업로드 → 여러 개 업로드 가능하게

**❌ 새로 만들어야 하는 것**:
- 조건부합격 프로세스
- 재심 관리 (대면/서면)
- 심사위원 불러오기 기능
- 서술형/척도형 평가표
- 부속서류 관리

## 4. 상세 수행방안

### 4.1 모든 단계에 평가표 적용 및 자동 이동

#### 4.1.1 현재 문제점
- 일부 단계는 평가표가 없어서 관리자가 수동으로 "통과" 처리
- 이렇게 하면 행정직원이 평가하는 것처럼 보임

#### 4.1.2 개선 방안

**원칙**:
- 모든 단계마다 평가표를 만들어야 함
- 평가 유형은 2가지:
  - **지도교수 단독**: 지도교수 혼자 평가 (예: 논문작성계획서)
  - **심사위원회**: 심사위원 3명 이상이 평가 (예: 본심사)

**자동 이동 조건**:
- 지도교수 단독: 지도교수가 평가를 완료하면
- 심사위원회: 모든 심사위원이 평가를 완료하면
- → 시스템이 자동으로 다음 단계로 이동

**예시**:

```
[논문작성계획서 단계]
학생이 계획서 제출
    ↓
지도교수가 평가표 작성 (합격/불합격 선택)
    ↓
평가 완료되면 자동으로 다음 단계(예비심사 1차)로 이동
```

```
[본심사 단계]
학생이 논문 제출
    ↓
심사위원 3명이 각각 평가표 작성
    ↓
3명 모두 평가 완료되면
    ↓
시스템이 자동으로 결과 계산
- 과반수 이상 합격 → 합격
- 조건부합격 1명 이상, 불합격 0명 → 조건부합격
- 그 외 → 불합격
    ↓
결과에 따라 자동 처리
- 합격: 다음 단계로 이동
- 조건부합격: 재심 프로세스 시작
- 불합격: 현재 단계에서 종료
```

#### 4.1.3 권한 정리

| 누가 | 평가 입력 | 단계 이동 | 현황 조회 |
|------|-----------|-----------|-----------|
| 지도교수 | ✅ (지도교수 단독 평가 단계) | 자동 | ✅ |
| 심사위원 | ✅ (심사위원회 평가 단계) | 자동 | ✅ |
| 관리자 | ❌ | ❌ (자동) | ✅ |

**핵심**: 관리자는 보기만 하고, 평가나 단계 이동을 직접 하지 않음

### 4.2 심사위원 불러오기 기능

#### 4.2.1 현재 문제점
- 예비심사를 3번(1차, 2차, 3차) 하면
- 매번 심사위원 3명을 다시 선택해야 함
- 똑같은 사람인데 3번 반복해서 선택하는 불편함

#### 4.2.2 개선 방안

**기능 추가**:
- 심사위원 배정 화면에 "이전 단계 심사위원 불러오기" 버튼 추가
- 버튼 클릭 시 이전 차수의 심사위원이 자동으로 입력됨
- 필요하면 수정 가능 (한 명 바꾸거나 추가/삭제)

**동작 방식**:

```
[예비심사 1차 심사위원 배정]
심사위원장: 홍길동 교수 선택
심사위원 1: 이순신 교수 선택
심사위원 2: 세종대왕 교수 선택
저장

[예비심사 2차 심사위원 배정]
"이전 단계 심사위원 불러오기" 버튼 클릭
    ↓
심사위원장: 홍길동 교수 (자동 입력)
심사위원 1: 이순신 교수 (자동 입력)
심사위원 2: 세종대왕 교수 (자동 입력)

필요하면 수정
저장
```

#### 4.2.3 주의사항

**언제 불러올 수 있나?**:
- 예비심사 1차 → 예비심사 2차: 불러오기 가능
- 예비심사 2차 → 예비심사 3차: 불러오기 가능
- 프로포절 → 예비심사: 불러오기 가능하지만 다를 수 있음
- 예비심사 → 본심사: 불러오기 가능하지만 다를 수 있음

**원칙**:
- 같은 종류의 심사(예비심사 내에서)는 같은 심사위원 사용이 일반적
- 큰 단계가 바뀔 때(프로포절→예비심사, 예비심사→본심사)는 바뀔 수 있음

### 4.3 조건부합격 및 재심 프로세스

#### 4.3.1 재심사와 지도단계의 관계 (구현 방식 결정)

**결정: 재심사는 별도 단계로 동적 생성**

**핵심 개념**:
- **워크플로우 템플릿**: 관리자가 생성하는 기본 단계 (재심 단계 미포함)
- **학생별 단계**: 템플릿을 복사하여 학생에게 배정, 조건부합격 시 재심 단계 추가
- **재심사**: 학생별로 독립적으로 단계가 추가됨 (다른 학생에게 영향 없음)

**구조**:
```
[워크플로우 템플릿] (관리자가 생성)
1. 연구계획서
2. 예비심사 1차 (allowReexam: true)
3. 예비심사 2차 (allowReexam: true)
4. 본심사 (allowReexam: true)
5. 최종논문

[학생 A - 조건부합격 발생 시]
1. 연구계획서 ✓
2. 예비심사 1차 ✓
3. 예비심사 2차 ✓
4. 본심사 → 조건부합격
5. 본심사(재심) ← 동적 생성
6. 최종논문

[학생 B - 조건부합격 없음]
1. 연구계획서 ✓
2. 예비심사 1차 ✓
3. 예비심사 2차 ✓
4. 본심사 ✓
5. 최종논문
```

**동작 방식**:
```
본심사 단계
    ↓ 평가 완료
[합격] → 최종논문으로 이동 (5번)
[조건부합격] → 학생의 단계 목록에 "본심사(재심)" 추가
              → 재심 단계로 이동 (4.5번)
              → 이후 단계들 order 재조정 (최종논문 → 6번)
[불합격] → 현재 단계 유지, 다음 학기 재신청
```

**장점**:
- 기존 단계 이동 로직 재사용 가능
- 학생별 독립적 관리 (다른 학생에게 영향 없음)
- 워크플로우 템플릿은 깔끔하게 유지
- 재심이 필요한 학생만 재심 단계 추가

#### 4.3.2 조건부합격이란?

**상황**:
- 학생이 논문을 제출했는데
- 불합격은 아니지만
- 일부 수정이 필요한 경우

**기존 방식의 문제**:
- 합격/불합격 2가지만 있으면
- 조금만 수정하면 될 학생도 "불합격" 처리해야 함
- 불합격하면 다음 학기까지 기다려야 함

**조건부합격 도입**:
- "수정 후 재심사"라는 옵션 제공
- 학생이 수정해서 다시 제출하면
- 재심사를 거쳐 최종 합격/불합격 결정
- **같은 지도단계 내에서 처리됨**

#### 4.3.3 데이터 구조 설계

**워크플로우 템플릿 (ThesisStage)** - 관리자가 생성:
```javascript
{
  id: 'TS001',
  name: '석사 표준 과정',
  stages: [
    { order: 1, name: '연구계획서', allowReexam: false },
    { order: 2, name: '예비심사 1차', allowReexam: true },
    { order: 3, name: '예비심사 2차', allowReexam: true },
    { order: 4, name: '본심사', allowReexam: true },
    { order: 5, name: '최종논문', allowReexam: false }
  ]
}
```

**학생별 단계 테이블 (StudentThesisStage)**:
```javascript
{
  studentId: '2024001',
  thesisStageId: 'TS001',

  // 학생별로 독립적인 단계 목록 (조건부합격 시 재심 단계 추가됨)
  customStages: [
    { order: 1, name: '연구계획서', isReexamStage: false },
    { order: 2, name: '예비심사 1차', isReexamStage: false },
    { order: 3, name: '예비심사 2차', isReexamStage: false },
    { order: 4, name: '본심사', isReexamStage: false },
```

**장점**:
- 학생별로 독립적인 단계 관리 (다른 학생에게 영향 없음)
- 워크플로우 템플릿은 깔끔하게 유지
- 재심 이력 자동 추적
- 기존 단계 이동 로직 재사용

#### 4.3.4 석사 본심사 조건부합격 프로세스

**전체 흐름**:

```
1. 학생이 본심사 논문 제출
   (지도단계: 본심사, 단계상태: 진행중, 심사차수: 1)

2. 심사위원 3명이 평가
   각자 합격/조건부합격/불합격 선택

3. 시스템이 자동으로 최종 결과 계산

4-A. 합격 → 다음 단계로 자동 이동
   (지도단계: 본심사 → 최종논문, 단계상태: 완료)

4-B. 조건부합격 → 재심 프로세스 (같은 단계 내)
   (지도단계: 본심사 유지, 단계상태: 재심사중, 심사차수: 2)
     ↓
   심사위원장이 재심 정보 입력
   - 재심 방식: 대면 또는 서면 선택
   - 재심 일정: 날짜 입력 (예: 2주 후)
   - 보완 요구사항: "연구방법론 부분 보완 필요" 등
     ↓
   학생에게 알림 발송
     ↓
   학생이 수정논문 + 수정전후대비표 제출
   (여전히 "본심사" 단계, 재심사 논문 제출)
     ↓
   재심 방식에 따라 처리:

   [대면 재심]
   - 심사위원장이 대면 재심 일정 설정
   - 심사위원 전원이 설정된 일정에 모여서 회의
   - 수정된 논문을 다시 심사 (재심 평가 진행)
   - 평가 완료 후 합격/불합격 최종 결정

   [서면 재심]
   - 심사위원장이 서면 재심 일정 설정
   - 심사위원장 또는 지도교수가 서류로만 확인
   - 재심 평가 진행 후 합격/불합격 최종 결정
     ↓
   재심 합격 → 다음 단계로 이동
   (지도단계: 본심사 → 최종논문, 단계상태: 완료)

   재심 불합격 → 현재 단계에서 종료
   (지도단계: 본심사 유지, 단계상태: 완료(불합격))
   다음 학기에 다시 "본심사" 단계부터 재신청

4-C. 불합격 → 현재 단계에서 종료
   (지도단계: 본심사 유지, 단계상태: 완료(불합격))
   다음 학기 재신청
```

**핵심**:
- 재심사는 "본심사" 단계 안에서 처리
- 단계상태: "진행중" → "재심사중" → "완료"
- 재심사를 위한 별도의 지도단계를 만들지 않음

#### 4.3.5 박사 본심사 조건부합격 프로세스

**박사 본심사 구조**:
- 박사는 본심사가 2번: 본심 1차, 본심 2차
- 이것은 **2개의 별도 지도단계**임 (재심사와는 다름)

**본심 1차 조건부합격**:
```
지도단계: 본심사 1차
    ↓
본심 1차 평가 → 조건부합격
    ↓
자동으로 "본심사 2차" 단계로 이동
(지도단계가 바뀜: 본심 1차 → 본심 2차)
(단, "이전 단계 조건부합격" 표시)
    ↓
본심 2차에서
- 1차 합격한 학생들
- 1차 조건부합격한 학생들
함께 심사
```

**본심 2차 조건부합격**:
```
지도단계: 본심사 2차
    ↓
본심 2차 평가 → 조건부합격
    ↓
**같은 "본심사 2차" 단계 내에서** 재심 프로세스
(지도단계 유지: 본심사 2차)
(단계상태: 진행중 → 재심사중)
    ↓
서면 재심 진행
(석사 본심의 서면 재심과 동일)
    ↓
재심 합격 → 다음 단계(최종논문)로 이동
재심 불합격 → 현재 단계 종료, 다음 학기 재신청
```

**핵심 차이점**:
- **본심 1차 → 본심 2차**: 지도단계가 바뀜 (다른 단계로 이동)
- **본심 2차 → 재심**: 지도단계 유지 (같은 단계 내 재심사)

#### 4.3.6 재심사 vs N차 심사 정리

**명확한 구분**:

| 구분 | 지도단계 | 심사차수 | 예시 |
|------|---------|---------|------|
| **N차 심사** | 다른 단계 | 각 단계의 1차 | 본심 1차(단계1) → 본심 2차(단계2) |
| **재심사** | 같은 단계 | 같은 단계의 2차 | 본심사(재심) |
| **예비심사 1,2,3차** | 다른 단계 | 각 단계의 1차 | 예비1차(단계1) → 예비2차(단계2) → 예비3차(단계3) |

**워크플로우 설정 예시**:

석사 과정:
```
1. 연구계획서 (지도단계1)
   └─ 재심 가능
2. 예비심사 1차 (지도단계2)
   └─ 재심 가능
3. 예비심사 2차 (지도단계3)
   └─ 재심 가능
4. 본심사 (지도단계4)
   └─ 재심 가능
5. 최종논문 (지도단계5)
```

박사 과정:
```
1. 연구계획서 (지도단계1)
2. 프로포절 (지도단계2)
3. 예비심사 1차 (지도단계3)
4. 예비심사 2차 (지도단계4)
5. 예비심사 3차 (지도단계5)
6. 본심사 1차 (지도단계6)
7. 본심사 2차 (지도단계7)
   └─ 재심 가능
8. 최종논문 (지도단계8)
```

**학교 메일 해석**:
- "N차, 재심의 경우 수정전후대비표 등 부속서류 제출"
  - N차 = 예비심사 1차, 2차, 3차, 본심사 1차, 2차 (각각 다른 지도단계)
  - 재심 = 조건부합격 후 같은 단계 내에서 재심사
  - 둘 다 부속서류를 제출함

#### 4.3.7 재심 일정 및 평가 설정

**누가 정하나?**:
- 심사위원장이 직접 입력

**심사위원장이 입력하는 정보**:
1. **재심 방식**: 대면 재심 / 서면 재심 선택
2. **재심 일정**: 재심 평가를 진행할 날짜 설정
3. **보완 요구사항**: 학생에게 어떤 부분을 수정해야 하는지 안내

**예시**:
- 본심사 평가일: 2026년 1월 20일
- 심사위원장이 재심 일정을 "2026년 2월 15일"로 설정
- 학생은 2월 15일까지 수정논문 제출
- 재심 방식이 "대면"이면 → 2월 15일에 심사위원 전원이 모여 평가
- 재심 방식이 "서면"이면 → 2월 15일까지 심사위원장 또는 지도교수가 평가

**재심 평가 제출**:
- 심사위원장이 재심 방식과 일정을 설정해야
- 학생이 수정논문을 제출할 수 있음
- 재심 평가가 완료되어야 최종 합격/불합격 결정

**기본 가이드** (학교 확인 필요):
- 대면 재심: 평가일로부터 4주 이내
- 서면 재심: 평가일로부터 2주 이내

### 4.4 평가표 유형 확장

#### 4.4.1 평가표 3가지 유형

**1) 점수형 평가표** (기존):
```
평가표: 본심사 평가표

항목 1. 연구 주제의 독창성 (20점)
       입력: [15] 점

항목 2. 연구 방법의 적절성 (20점)
       입력: [18] 점

항목 3. 연구 결과의 기여도 (30점)
       입력: [25] 점

항목 4. 논문 구성 및 표현 (30점)
       입력: [22] 점

총점: 80점 / 100점
합격 기준: 70점 이상
→ 합격
```

**2) 서술형 평가표** (신규):
```
평가표: 논문작성계획서 평가표

항목 1. 연구 주제
        (연구 주제의 명확성과 실현 가능성을 평가)
입력: [연구 주제가 명확하고 실현 가능하다.
      다만 연구 범위를 좀 더 구체적으로 제한할 필요가 있다.]

항목 2. 연구 계획
        (연구 일정 및 방법론의 타당성을 평가)
입력: [연구 일정은 적절하나 설문조사 대상자 선정 기준을
      명확히 할 필요가 있다.]

항목 3. 종합 의견
입력: [전반적으로 우수하나 위 사항 보완 바람]

최종 판정: ○ 합격  ○ 불합격
```

**3) 척도형 평가표** (신규):
```
평가표: 예비심사 평가표

항목 1. 연구 주제의 독창성
선택: ○ 매우 미흡  ○ 미흡  ○ 보통  ● 우수  ○ 매우 우수

항목 2. 연구 방법의 적절성
선택: ○ 매우 미흡  ○ 미흡  ● 보통  ○ 우수  ○ 매우 우수

항목 3. 연구 결과의 기여도
선택: ○ 매우 미흡  ○ 미흡  ○ 보통  ● 우수  ○ 매우 우수

(더 많은 항목...)

합격 조건: 모든 항목이 "보통" 이상
→ 합격
```

#### 4.4.2 종합평정 기능

**필요성**:
- 심사위원이 여러 명일 때
- 각자 평가는 했지만 최종적으로 누군가는 "이 학생은 합격/조건부합격/불합격"이라고 정해야 함

**구현 방안**:
- 심사위원장이 모든 심사위원의 평가를 보고
- 종합 의견 작성
- 최종 합격/조건부합격/불합격 결정

**예시**:
```
심사위원 1 평가: 80점
심사위원 2 평가: 75점
심사위원 3 평가: 70점
    ↓
심사위원장 종합평정:
"3명의 심사위원 평가를 종합한 결과,
전반적으로 우수한 연구이나 연구방법론 부분 보완이 필요함.
따라서 조건부합격 처리하고 보완 후 재심사 진행"

최종 결정: 조건부합격
```

### 4.7 학생 피드백 답변 기능

#### 4.7.1 현재 상황

- 교수님이 새 버전 볼 때 "학생이 어디를 어떻게 수정했는지" 찾기 어려움

## 5. 구현 우선순위

### 5.1 왜 순서가 중요한가?

- 모든 기능을 한꺼번에 만들면 시간이 오래 걸림
- 중요한 것부터 먼저 만들어서 빨리 확인받아야 함
- 학교에서 "이건 아니다"라고 하시면 빨리 수정 가능

### 5.2 3단계 개발 계획

#### 5.2.1 Phase 1: 필수 기능 (2주)

**목표**: 학교 메일에서 최우선으로 요청한 것

| 무엇을 | 왜 중요한가 | 기간 |
|--------|-------------|------|
| 모든 단계 평가표 필수 | 심사자 직접 평가 원칙 | 2일 |
| 자동 단계 이동 | 관리자 손 안 가게 | 3일 |
| 조건부합격 상태 추가 | 기본 구조 만들기 | 1일 |
| 재심 프로세스 (기본) | 조건부합격 처리 | 5일 |
| 부속서류 업로드 | 여러 파일 올리기 | 3일 |

**이 단계가 끝나면**:
- 학교에 보여드리고 확인받기
- "이 방향 맞다" 확인받으면 다음 단계 진행

#### 5.2.2 Phase 2: 중요 기능 (2주)

**목표**: 사용 편의성 높이기

| 무엇을 | 왜 중요한가 | 기간 |
|--------|-------------|------|
| 심사위원 불러오기 | 반복 작업 줄이기 | 2일 |
| 서술형 평가표 | 평가 방식 다양화 | 3일 |
| 척도형 평가표 | 평가 방식 다양화 | 3일 |
| 재심 프로세스 (고급) | 대면/서면 구분, 평가 설정 | 6일 |

#### 5.2.3 Phase 3: 개선 사항 (3주)

**목표**: 사용성 향상 및 필수 기능 추가

| 무엇을 | 왜 중요한가 | 기간 |
|--------|-------------|------|
| 논문지도 자료실 | 교수-학생 자료 공유 필수 | 7일 |
| 학생 피드백 답변 | 소통 개선 | 4일 |
| 제출물 삭제 조건 | 실수 방지 | 2일 |
| 알림 시스템 | 놓치는 일 없게 | 3일 |
| 대시보드 개선 | 한눈에 보기 | 3일 |

**논문지도 자료실 상세**:
- 게시글 CRUD (3일)
- 학생 선택 UI 및 필터 (2일)
- 댓글 기능 (1일)
- 파일 업로드 및 권한 관리 (1일)

**비필수 기능** (저우선순위):
- ZIP 전체 다운로드: 개별 다운로드로도 충분하므로 필요 시 추가 검토
- 캘린더 뷰: 실시간 예약 기능은 이미 구현되어 있으므로 추가 UI 개선은 후순위

### 5.3 전체 일정 (9주)

```
1주차: Phase 1 (필수 기능) 시작
2주차: Phase 1 완료, 학교 중간 검토
       ↓
3주차: Phase 2 (중요 기능) 시작
4주차: Phase 2 완료, 학교 중간 검토
       ↓
5주차: Phase 3 (개선 사항 + 자료실) 시작
6주차: Phase 3 계속
7주차: Phase 3 완료
       ↓
8주차: 전체 통합 테스트, 버그 수정
       ↓
9주차: 학교 최종 테스트, 피드백 반영
```

**일정 변경 이유**:
- 논문지도 자료실 기능 추가로 Phase 3가 1주 연장
- 전체 개발 기간: 8주 → 9주

## 7. 학교 확인 질의사항

### 7.1 조건부합격 프로세스 확인

**제목**: 조건부합격 및 재심 프로세스 구현 방안 확인 요청

**내용**:

안녕하세요. 메일로 주신 조건부합격 프로세스를 아래와 같이 구현하려고 합니다.
학교 운영 방식과 맞는지 확인 부탁드립니다.

#### 7.1.1 구현할 내용

**1) 평가 결과에 조건부합격 추가**
- 기존: 합격 / 불합격
- 변경: 합격 / 조건부합격 / 불합격

**2) 석사 본심사 프로세스**
```
본심사 평가
    ↓
조건부합격 판정
    ↓
심사위원장이 재심 정보 설정
- 재심 방식: 대면 또는 서면
- 재심 일정: 재심 평가를 진행할 날짜
- 보완 요구사항: 내용 입력
    ↓
학생에게 알림 발송
    ↓
학생이 재심 일정까지 수정논문 + 부속서류 제출
    ↓
[대면 재심]
재심 일정에 심사위원 전원 회의
→ 평가 진행 → 최종 합격/불합격

[서면 재심]
재심 일정까지 심사위원장 또는 지도교수 확인
→ 평가 진행 → 최종 합격/불합격
    ↓
재심 합격 → 논문 과정 완료
재심 불합격 → 다음 학기 재신청
```

**3) 박사 본심사 프로세스**
```
본심 1차 조건부합격
    ↓
자동으로 본심 2차로 이동
(조건부합격 표시)
    ↓
본심 2차에서
1차 합격자 + 1차 조건부합격자 함께 심사
    ↓
본심 2차 조건부합격
    ↓
서면 재심 진행
```

#### 7.1.2 확인이 필요한 사항

**질문 1**: 재심사와 지도단계 구조 (중요!)
- 우리가 이해한 구조가 맞는지 확인이 필요합니다:

```
[우리가 이해한 방식]
지도단계: 본심사 (하나의 단계)
├─ 최초 심사 (심사차수 1)
│  └─ 조건부합격 시
└─ 재심사 (심사차수 2, 같은 "본심사" 단계 내)
   └─ 합격 → 다음 단계(최종논문)로 이동

즉, 재심사는 별도의 지도단계가 아니라
같은 단계 안에서 "재심사 상태"로 관리
```

이 방식이 맞나요? 아니면 "재심사"를 별도의 지도단계로 만들어야 하나요?

**질문 2**: 박사 본심 1차 조건부합격
- "본심 2차에서 재심사"의 의미가
- A) 본심 1차 조건부합격 → 본심 2차 단계로 이동 (단계가 바뀜)
- B) 본심 1차 단계 안에서 재심 → 합격 후 본심 2차로 이동

우리는 A로 이해했는데 맞나요?

**질문 3**: N차 심사와 재심사 구분
- 메일에 "N차, 재심의 경우 수정전후대비표 제출"이라고 되어 있는데:
  - N차 = 예비심사 1차, 2차, 3차 (각각 **다른 지도단계**)
  - 재심 = 조건부합격 후 **같은 지도단계 내** 재심사
- 이렇게 이해한 것이 맞나요?

**질문 4**: 재심 횟수
- 재심에서 불합격하면 같은 학기에 다시 재심 기회가 있나요?
- 아니면 해당 학기는 종료되고 다음 학기에 처음부터 다시 신청하나요?

**질문 5**: 대면 재심 vs 서면 재심
- 대면 재심: 심사위원 전원 참석이 필수인가요?
- 서면 재심: "지도교수에게 위임"의 의미가, 심사위원장이 지도교수에게 재심 권한을 넘기는 것인가요?

**질문 6**: 재심 일정과 평가
- 심사위원장이 "재심 일정"을 설정하면, 해당 일정에 재심 평가를 진행하는 것이 맞나요?
- 재심 방식(대면/서면)을 설정해야 학생이 수정논문을 제출할 수 있도록 하는 것이 맞나요?
- 재심 평가가 완료되어야 최종 합격/불합격이 결정되는 것이 맞나요?

**질문 7**: 재심 일정 가이드
- 재심 일정에 대한 기본 가이드가 있나요? (예: 평가일로부터 2주 이내, 4주 이내 등)

#### 8.2.2 워크플로우 무결성 보장 (P0 - 핵심 설계 변경)

**구현 난이도**: 🟢 **하** (2/5)

**문제 상황**:
초기 재심사_구현방식_결정.md에서 제안한 방식:

```javascript
StudentThesisStage {
```

- ❌ 버그 발생 가능성 높음

**최종 해결 방안** (재심사_구현방식_최종.md):

```javascript
    { order: 3, name: '최종논문', allowReexam: false }
  ]
}

// StudentThesisStage: 변경 없음
StudentThesisStage {
  currentStageOrder: 2,  // ← 재심 중에도 2 유지!
}

// ExaminationHistory: 재심 차수로 관리
ExaminationHistory [
  { examRound: 1, result: '조건부합격', stageOrder: 2 },

]
```

**난이도 낮은 이유**:
1. **기존 구조 그대로 유지**: ThesisStage, StudentThesisStage 변경 최소
2. **단순 필드 추가**: allowReexam 플래그만 추가 (boolean, default: false)
3. **별도 테이블 관리**: ExaminationHistory에서 재심 차수 관리

**리스크**:
- 🟢 **Low**: 기존 코드 영향 최소
- 🟢 **Low**: 워크플로우 무결성 보장

**대응 방안**:
1. ThesisStage.stages[].allowReexam 필드 추가
2. 관리자 화면에서 단계별 재심 허용 여부 설정 UI 제공
3. currentStageOrder는 절대 동적으로 변경하지 않음 (재심 중에도 유지)

---

#### 8.8.3 단위 테스트 필수

✅ **핵심 함수 단위 테스트 체크리스트**:
- [ ] getNextExamRound() - 4가지 케이스 (이력 없음→1, 이력 1건→2, 이력 3건→4, 재신청→1)
- [ ] processEvaluationResult() - 3가지 결과 분기 (합격, 조건부합격, 불합격)
- [ ] canEvaluateReexam() - 3가지 권한 케이스 (초기 심사, full, chair_only)
- [ ] processReapplication() - 자격 검증 + 생성 로직

#### 8.8.4 FSM 다이어그램 작성

✅ **ThesisApplication 상태 전환 다이어그램**:
```
application_submitted (신청 접수)
  ↓ (관리자가 심사위원 구성)
committee_assigned (심사위원 구성 완료)
  ↓ (학생이 논문 제출)
thesis_submitted (논문 제출 완료)
  ↓ (심사위원장이 일정 설정)
exam_scheduled (심사 일정 확정)
  ↓ (심사 진행)
under_evaluation (심사 진행 중)
  ↓ (평가 완료)
completed / failed (완료 / 실패)
```

### 8.9 기타 기술적 어려움 (기존 항목 유지)

#### 8.9.1 파일 업로드 실패

**문제**:
- 파일이 너무 크거나 인터넷이 느리면 업로드 실패
- 학생이 "제출했는데 안 올라갔다" 상황 발생

**해결방안**:
- 파일 크기 제한 명확히 안내 (20MB)
- 업로드 진행률 표시 (0% → 100%)
- 업로드 실패 시 명확한 오류 메시지
- 재시도 버튼 제공

#### 8.9.2 PDF 뷰어 성능

**문제**:
- 논문이 200페이지가 넘으면 PDF 뷰어가 느려질 수 있음

**해결방안**:
- 페이지별로 나눠서 로딩
- 썸네일은 미리 만들어서 캐싱
- 100MB 이상 파일은 경고 메시지

#### 8.9.3 평가표 유형 다양성

**문제**:
- 학교마다 평가표가 다 다를 수 있음
- 3가지 유형(점수/서술/척도)으로 모두 커버 가능한가?

**해결방안**:
- 기본 3가지 유형 먼저 구현
- 나중에 확장 가능한 구조로 설계
- 학교에서 실제 사용하는 평가표 미리 받아서 확인

## 9. 결론

### 9.1 핵심 구현 방향 요약

**1) 모든 단계에 평가표 필수**
- 심사자(교수/심사위원)가 직접 평가
- 평가 완료되면 자동으로 다음 단계 이동
- 관리자는 조회만 가능

**2) 조건부합격 및 재심**
- 합격/조건부합격/불합격 3가지로 구분
- 조건부합격 시 재심 프로세스 진행
- 재심 방식: 대면(회의) 또는 서면(문서)
- 재심 기한은 심사위원장이 직접 설정

**3) 심사위원 관리 편의성**
- N차 심사 시 이전 차수 심사위원 불러오기
- 불러온 후 수정 가능

**4) 평가표 다양화**
- 점수형 (기존)
- 서술형 (신규)
- 척도형 (신규)
- 심사위원장 종합평정 기능

**5) 부속서류 관리**
- 주 논문 1개 + 부속서류 여러 개 업로드
- ZIP 파일로 한 번에 다운로드

### 9.2 시스템 근간 유지

**바꾸지 않는 것**:
- 워크플로우 레고 블록 방식
- 단계 유형 → 워크플로우 조립 → 학생 배정 흐름
- 기존 UI/UX 구조

**추가하는 것**:
- 기존 구조에 기능 추가
- 새로운 상태값 추가 (조건부합격, 재심 등)
- 자동화 로직 추가

### 9.3 기대 효과

**운영 효율성**:
- 심사 프로세스 자동화 → 관리자 일 줄어듦
- 단계 이동 자동화 → 놓치는 학생 없음
- 명확한 권한 분리 → 책임 소재 분명

**사용자 편의성**:
- 심사위원 불러오기 → 반복 작업 감소
- 부속서류 한 번에 다운로드 → 편리함
- 진행 상황 시각화 → 한눈에 파악

**시스템 안정성**:
- 기존 구조 유지 → 리스크 적음
- 단계별 개발 → 안정성 확보
- 모든 변경 로그 기록 → 추적 가능
