## 1. 재정비 기준

1. **명시된 요구사항만 구현**: 요구사항정의서(JXLB-1·2·7)에 명시되지 않았고 필수도 아닌 항목은 구현하지 않는다(이미 구현한 것은 걷어낸다).
2. **기존 목업 재사용**: 화면·로직·버튼·상태값·용어는 수정 전 목업(태그 `before-re-review-mockup`)에 있던 것을 최대한 그대로 쓴다. 새 디자인(새 팝업·배지·안내 박스·색상 등)은 하지 않는다.
3. **불가피한 경우만 추가**: 요구사항을 화면에서 보여 주는 데 꼭 필요한 로직·정보만 추가한다.
4. **관리자 화면은 관리 목적만**: 재신청·재심사 건을 일부러 구분해 보여 주지 않는다.

## 2. 질문에 대한 답

### 2-1. 교수 승인 화면의 '이전 차수 이력'은 명시적 요구사항인가? → **아니오 (제외)**

요구사항정의서에 있는 이력 관련 문장은 아래 셋뿐이다.

| 요구 | 원문 | 화면 요구 여부 |
|---|---|---|
| JXLB-1 | "기존 심사 결과·평가표·의견은 삭제하지 않고 '1차' 이력으로 보존함" | 보존(데이터)만 요구 |
| JXLB-1 | "[모든 재심사 건]에 대해 [차수(1차, 2차 등)]를 부여하여 기존 심사 이력과 명확히 구분 및 관리함" | 차수 부여·구분 |
| JXLB-2 | "학생은 심사 신청 기간 여부와 관계없이 구 이력(불합격 총평)을 상시 조회할 수 있도록 구현함" | **학생** 조회만 명시 |

교수 승인 화면에서 이전 차수 이력을 보여 달라는 요구는 없다. → 제거한다.

### 2-2. "철회는 심사 미진행일 때만 가능한데, 채점 완료 내역이 남아 있는 게 말이 되는가?" → **현재 목업에서는 맞지 않음 (제거)**

- 요구서의 "철회 처리 시에도 이미 심사/채점이 완료된 세부단계 내역은 삭제하지 않고 보존"은 **한 기본단계 안에 세부단계가 여러 개**인 경우를 말한다. 요구서 예시도 "본심사 1차(세부단계) 합격 & 본심사 2차(세부단계) 미채점 → 본심사 철회 시 1차 결과 유지"이다.
- 목업은 기본단계마다 세부단계가 1개라서, 철회할 수 있는 상태(채점 0건)에서는 보존할 채점 내역이 존재하지 않는다.
- 현재 목업이 '보존'으로 표현한 것은 이전 학기 불합격 기록이었다. 이것은 철회와 상관없는 별개의 신청이므로 철회 설명에 끼워 넣을 이유가 없다.
- **조치:**
  - 철회 관련 설명·처리에서 "결과 확정 기록 보존" 표현과 로직을 걷어낸다.
  - 요구서의 팝업 문구 2종("심사가 진행중이므로 철회할 수 없습니다." / "해당 단계에서 제출한 자료와 내역은 모두 초기화됩니다(합격여부가 결정된 단계 제외) 그래도 철회하시겠습니까?")은 요구서 원문이므로 그대로 쓴다.

## 5. 진행 방법

1. 결정 D1~D4 확정
2. 학생 → 교수 → 관리자 순으로 제거·원복 (화면별 커밋, 롤백 가능)
3. 테스트 갱신 · 알파테스트
4. main 병합 · push · Vercel 배포 확인
5. 기능정의서·질의서 재작성 (커밋 제외), 실제 배포 주소에서 링크 재검증

**완료 조건**
- 학생: 논문신청 상태가 미신청 / 신청완료 / 재심사 진행만 나오고, 버튼은 [관리] / [철회]뿐임
- 학생: 구 이력(불합격 총평)을 기존 화면 요소로 언제든 조회할 수 있음
- 교수: 심사 목록과 상세가 기존 모습 그대로이고(차수 컬럼 제외), 조건부합격 시 다음 심사 행이 생김
- 관리자: 신청구분, 철회·재심사 대상·배정 불가 상태, 차수 표시가 없음
- 테스트 통과, 배포 링크 정상
